# What the Hexlet project requires of Call Calendar

Research for [#9](https://github.com/arkadiy93/ai-for-developers-project-386/issues/9), part of the map [#8](https://github.com/arkadiy93/ai-for-developers-project-386/issues/8). Done on 2026-10-15.

## Summary

- The course wants **Design First**. The API contract is written in **TypeSpec**, and **OpenAPI is generated from it**. A **frontend client SDK** and **server artifacts** (types, request validation, routes) are then generated from the OpenAPI. The whole chain has to run with one command, and generated files are never edited by hand. The course names no file location for the contract. The only rule is that it lives in the repo. [S1 step 40]
- The course expects the **app spec to be published in the issue tracker** (through `/to-spec`), not as a file in the repo. After that it is split into tickets with declared dependencies (through `/to-tickets`). [S1 step 40]
- Functional scope: one predefined Owner with no auth. The Owner **creates Event Types** (id, name, description, duration in minutes) and **sees one list of upcoming Bookings of every type**. The Guest **browses Event Types**, **picks one**, **picks a free Slot within 14 days from today**, and **books it**. No two Bookings may share a time, even across Event Types. The rules are enforced **on the server**. [S1 step 40, step 50]
- Mentor review also checks **"slots of 30 minutes"**, a **clear message on a slot conflict**, and that the **live API matches the contract**. [S1 checklist]
- Hexlet's automated check (`hexlet-check.yml`) knows nothing about the contract or about bookings. When it runs, it builds the **`Dockerfile` in the repo root**, starts the container with **`PORT=8080`**, and expects **`GET /` → 200**. Right now our runs skip this step ("Tests will run during review step"). [S1 checklist, S3, S4, S5]

## Functional requirements (S1 step 40, "Что должно уметь приложение")

Roles: there is an Owner (владелец календаря) and there are Guests. **There is no registration and no auth.** The Owner is "один заранее заданный профиль, который по умолчанию используется в админской части" (one predefined profile that the admin part uses by default).

**Owner can:**

- Create Event Types. For each one the Owner **sets the id, name, description and duration in minutes**.
- View the upcoming-meetings page, where **Bookings of all Event Types are shown in one list**.

**Guest:**

- Views the page of Event Types with each type's name, description and duration.
- Picks an Event Type, opens a calendar, and picks a free Slot **in the next 14 days**.
- Creates a Booking on that Slot.

**Rules:**

- Two Bookings can't be made for the same time, **even when their Event Types differ**.
- Available Slots are generated for **14 days starting from the current date**, and a Guest can book only a free Slot inside that window.
- "Internal implementation, stack and structure are yours. Here we agree on the external behavior: the scenarios, the data passed, and the booking constraints."

**Things added in step 50 and the checklists:**

- The end-to-end Guest flow covers Event Type, calendar, free Slot, booking, and **confirmation**.
- A taken Slot is never offered as free. Rebooking it fails, including through another Event Type, and **the user sees a clear conflict message**. [checklist]
- Booking rules are enforced on the server, so a direct API request can't get around them. [step 50, review-checklist]
- **"Окно записи 14 дней, слоты по 30 минут"** (14-day booking window, 30-minute slots). [checklist, review-checklist]
- The live API matches the contract: paths, methods, field names and status codes. [step 50, review-checklist]

The steps do **not** require editing or deleting Event Types, cancelling Bookings, or any particular Guest fields. "What next" lists flexible schedules, time zones, accounts, calendar integrations, notifications, cancel/reschedule and buffers as **later** features. [checklist]

## Contract format, tooling and location (S1 step 40)

- Write the contract in **TypeSpec** and **generate OpenAPI from it**. Hand-written OpenAPI is explicitly discouraged.
- The chain: `TypeSpec → OpenAPI → client SDK (frontend)` and `→ types, request validation, routes (backend)`. The suggested tools are [openapi-ts / Hey API](https://heyapi.dev/) for the SDK and [OpenAPI Generator](https://openapi-generator.tech/) for server stubs. You pick tools that fit your stack.
- Generation commands live in a `Makefile` or package scripts, and **the whole chain repeats with one command**. Generated files are **not edited by hand**.
- Step 40 requirements say: "В репозитории есть TypeSpec-контракт, покрывающий сценарии владельца и гостя" (the repo has a TypeSpec contract that covers the Owner and Guest scenarios). It also asks for an OpenAPI generated from it, with the command documented, an SDK generated, and server artifacts generated.
- **File location: not specified.** The reference solution keeps `code/src/main.tsp` and `code/tspconfig.yaml`, which emit `tsp-output/@typespec/openapi3/openapi.yaml` (generated output is committed there). It also has a `dev:prism` script that mocks the API from the generated OpenAPI with Prism.
- **The spec document** is published **to the tracker** by `/to-spec`. It holds user stories, implementation decisions and _testing decisions_ (the boundaries the app is tested at). Then `/to-tickets` makes vertical tickets (contract, server, UI, tests) with declared blockers. The mentor looks for: a map with the `wayfinder:map` label whose tasks are closed with answers, a spec issue, tickets with dependencies, tickets that link to the spec, and commits that link to tickets. [review-checklist]

### The reference contract (S1 `code/src/main.tsp`, for orientation only)

The mentor checklist says the reference "служит ориентиром по смыслу: стек и структура каталогов у студента свои" (a guide to meaning only; the student's stack and folders are their own). Its main points:

- `GET /api/event-types`. `GET /api/event-types/{slug}/availability` returns `{startTime, endTime, isAvailable}[]`.
- `GET|POST /api/admin/event-types`, `GET|PATCH|DELETE /api/admin/event-types/{id}`.
- `GET|POST /api/bookings`. A Booking has `eventTypeId/Slug/Name`, `startTime`, `endTime`, `clientName`, `clientEmail`, `notes`, `bookedAt`.
- An EventType has `id`, `slug`, `name`, `description`, `durationMinutes`, `publicUrl`. The id is generated, and the Owner supplies a `slug`.
- No error models are declared in the TypeSpec.
- Slots (`src/slots.ts`, `src/config.ts`): 09:00–18:00 **UTC**, back-to-back slots that step by the **Event Type's duration**, 14 days starting **tomorrow** by default (`SLOT_BASE_DATE`). Overlap is checked with interval intersection.
- The UI ships two Event Types, 15 min and 30 min. The Owner is shown as "Tota / Host" on the booking catalog. The admin pages are `/admin/events` and `/admin/event-types`.

## How later steps use the contract

- **Code generation** (step 40): the SDK for the frontend, and types, validation and routes for the backend, all from the generated OpenAPI with one command.
- **Implementation** (step 50): the frontend must call the API through the SDK. A contract change goes TypeSpec, then generate, then both sides. The mentor compares the live API to the contract.
- **Tests** (steps 30 and 50): `/implement` writes tests at the boundaries fixed in the spec's testing decisions. Browser E2E covers the main booking flow and the slot conflict, and has to be green in GitHub Actions.
- **Deployment** (step 60): a Docker image with the frontend and API served from one container on `$PORT`, plus a public URL in `README.md`. The contract has no direct role here.

## What `hexlet-check.yml` checks (S4, S5, S1 `docker-compose.yml`, `Makefile`, `__tests__/`)

- The action loads the project member from Hexlet's API. If `tests_on` is false, it logs `Tests will run during review step` and passes. **This is what happens in our runs now** (S5, run 38754752111).
- When tests are on, it copies our repo into the project image as `/project/code`, runs `make setup`, which does `docker build -f code/Dockerfile code` (our **root `Dockerfile`**), and starts the app with `docker run -e PORT=8080 …`. It then runs the `test` service: one Playwright test, `page.goto('/')` → status **200**. The healthcheck is `curl http://localhost:8080/`.
- The package-name check (`@hexlet/code` for JS projects) is skipped, because `spec.yml` sets `language: other`. Our root package name doesn't matter.
- What this means for us: the repo has **no root `Dockerfile` yet**, and the backend defaults to port 3000 and only serves `/api`. To pass, one container must serve the built frontend at `/` and listen on `$PORT`. This is implementation and deployment work, outside the spec map.

## Implications for map #8

- **The destination may need rewording.** #8 says "a spec document in the repo… approval means the merge". The course expects the spec **in the tracker** (a `/to-spec` issue) plus a **TypeSpec contract in the repo**, and then tickets from `/to-tickets`. One option is to keep the repo document and also publish the spec issue. Either way, the destination should say "an approved spec that tickets can be cut from".
- **The contract format is decided by the course:** TypeSpec, then OpenAPI, then generated SDK and server artifacts, all with one command. The "API surface" fog item can now say TypeSpec. A new ticket could settle where the `.tsp` file lives (for example a new `packages/contract` workspace or `apps/backend`) and which generators to use. Tool choice is arguably implementation, though the course lists it under step 40.
- **New tickets the gaps suggest:** (1) the Slot grid against "30-minute slots" against quarter-hour starts and Event Type durations; (2) who sets the Event Type id or slug, and the URL key; (3) the time zone for Working Hours and Slots; (4) the error model and Guest-facing message for a Slot conflict (fits inside the "API surface" fog); (5) the testing decisions the `/to-spec` output must include (the boundaries for E2E and API tests). That last one conflicts with "test strategy" being out of scope in #8, because the course wants testing decisions inside the spec.
- **Out of scope as #8 says, but required later:** a root `Dockerfile`, one container serving frontend and API, the `$PORT` env var (checked with 8080), and a public URL in `README.md`.
